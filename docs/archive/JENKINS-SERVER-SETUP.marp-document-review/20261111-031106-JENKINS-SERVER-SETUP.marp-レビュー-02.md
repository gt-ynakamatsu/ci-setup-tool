### [重要] Groovy の戻り値の判定が未検証で、API Token とプラグインの失敗時の対処が「再実行」だけになっている

- 対象箇所: 「主なエラーと対処（エージェント・Token）」の `API Token を発行できませんでした` 行の「結果表示を確認して再実行。成功するまでトークンファイルは作成されない」。「主なエラーと対処（JDK・Jenkins）」の `プラグインの導入に失敗しました` 行の「Jenkins 更新サイトへの通信を確認して再実行」
- 問題: スクリプトは、API Token の Groovy の戻り値をそのまま `Test-ApiTokenText`（`^[0-9a-fA-F]{32,64}$`）で判定する。Jenkins の `/scriptText` が戻り値の前に `Result: ` を付ける場合、トークンは Jenkins 側で発行済みなのに判定が必ず失敗し、`API Token を発行できませんでした。結果: Result: <トークン>` で停止する。この場合、再実行しても毎回同じところで止まる。そのたびに `cisetup` という名前のトークンが Jenkins に1つずつ増え、エラー表示にはトークンの値がそのまま出る。プラグイン導入の Groovy は、`deploy()` の後で `pm.isRestartRequiredForCompletion()` を呼ぶ。`PluginManager` にこのメソッドがない場合、取得は済んでいるのに「プラグインの導入に失敗しました」で止まる。取得しただけのプラグインは再起動するまで読み込まれないため、再実行するとまた未導入と判定され、同じ失敗を繰り返すおそれがある。
- 理由: 手順書の「検証状況」は、プラグイン導入から API Token 発行までが実機で未確認だと正しく書いている。しかし、エラー表の対処は、再実行すれば回復するという前提で書かれている。上のどちらかが当たると、完了条件である接続テストまで進めない。原文の「検証状況」によれば、前回の実機確認でも、同じプラグイン用 Groovy の `pluginManager.updateCenter` が存在せず失敗している。同種の失敗が残っていないとは言えない。
- 修正案: 通し実行で2点を確かめ、その結果をエラー表に反映する。確かめる前に配布する場合は、2行に次の案内を加える。API Token の行には「エラー表示に16進の値が出ていれば、それが発行済みのトークン。再実行を繰り返さず、検証環境の担当へ連絡する」と書く。プラグインの行には「再実行しても同じ表示なら、Jenkins を再起動してから再実行する」と書く。
- 確認事項: `/scriptText` の出力形式と、`PluginManager.isRestartRequiredForCompletion()` が存在するか。どちらも参照資料の外にある Jenkins 本体の仕様で、このレビューでは確かめていない。`Result: ` が付くことが確かめられた場合、この指摘は手順が完了できない重大な問題になる。

### [重要] 「検証状況」から実施した環境と範囲が消え、Windows Server で動かしていないことが読み取れない

- 対象箇所: 「検証状況」の「この手順は、次の実装と照合しています。」と、未確認項目の箇条書き
- 問題: 原文の「検証状況」には次の内容があった。2026-11-11 に Windows Sandbox でスクリプトを実行し、Git 2.47.1、.NET SDK 8.0.428、JDK 21.0.13 の導入、Jenkins の起動、管理者ログインまで進んだ。手作業での確認時の Jenkins は 2.580.2 で、Java 17 では起動しなかった。CISetup の「Jenkins サーバー初回設定」は、検証環境でノード作成が HTTP 400 になった。改稿では、これらがすべて「実装と照合しています」に置き換わった。そのため、実機で何をどこまで動かしたのか、そもそも動かしたのかが読み取れない。Windows Sandbox は Windows のクライアント版の上で動くため、対象である Windows Server では一度も動かしていないことになるが、その点も分からなくなった。手順書には対象 OS の版もない。
- 理由: 読み手のインフラ担当は、検証環境で何を通し実行すべきかを、この情報から判断する。スクリプトは TLS のプロトコルを指定せずに `Invoke-WebRequest` で HTTPS の配布元から取得する。古い Windows Server の Windows PowerShell 5.1 では TLS 1.2 が既定で使われず、最初のダウンロードで止まることがある（参照資料の外の一般的な事象で、このレビューでは確かめていない）。HTTP 400 の件が消えたため、「Jenkins サーバー初回設定」を使わない理由も、実際に失敗したという事実から設計上の話へ弱まった。
- 修正案: 実施日、実施環境（Windows Sandbox）、確認できた工程と版、未確認の工程を一覧に戻す。Windows Server で未確認であることと、動作を確認した OS の版、または対象とする OS の版を書く。「導入される版と方式」の理由に、検証で HTTP 400 になったことを一文で戻す。
- 確認事項: 対象とする Windows Server の版で、スクリプトのダウンロードが TLS の設定を変えずに通るか。

### [重要] 「Jenkins が終了しました」の表示は、実際のウィンドウでは文字化けする可能性が高い

- 対象箇所: 「プラグイン反映時の再起動」の「最初の Jenkins ウィンドウには、次の表示が残ることがあります。」とそのコード例
- 問題: スクリプトは `start-jenkins.bat` と `start-agent.bat` を `UTF8Encoding($false)`、つまり BOM なしの UTF-8 で書き出す。バッチの中に `chcp 65001` はない。`cmd.exe` はバッチを OEM コードページで読むため、日本語版 Windows（コードページ 932）でも英語版でも、`echo Jenkins が終了しました。上の表示を確認してください。` の日本語部分は化けて表示される。読み手が見るのは `Jenkins` の後に意味の通らない文字が続く行で、スライドに示した文言とは一致しない。`start-agent.bat` の「エージェントが終了しました」も同じである。
- 理由: このスライドは、正常な再起動とエラーを見分けるために、表示の文言を示している。文言が一致しないと、読み手は表示を照合できない。その結果、新しい Jenkins ウィンドウを閉じるなどの誤った判断を招く。
- 修正案: 文言での照合をやめ、表示の特徴で見分けるよう書き換える。たとえば「最初のウィンドウには、Jenkins の終了ログの後に『続行するには何かキーを押してください』が出て止まる（日本語は文字化けすることがある）」とする。あわせて、新しいウィンドウが開いていることを判断の基準にする。
- 確認事項: 対象サーバーで「ベータ: ワールドワイド言語サポートで Unicode UTF-8 を使用」が有効だと、文字化けしない。実機でどう表示されるかを確認する。

### [重要] エージェント待ちで止まったときのウィンドウの扱いが、スクリプトの表示と逆になっている

- 対象箇所: 「再実行の原則」の「原因調査のために手動起動したウィンドウを、再実行前に閉じる必要はありません。」。「主なエラーと対処（エージェント・Token）」の「必要なら `start-agent.bat` を起動し、そのまま同じコマンドを再実行」
- 問題: スクリプトのエラー表示は「エージェントのウィンドウを閉じ、start-agent.bat を別のウィンドウで実行してください。」と案内している。手順書は閉じなくてよいとしており、画面の案内と逆になっている。スクリプトは、`agent.jar` を含む java.exe が動いていれば、エージェントを起動し直さない。`start-agent.bat` も書き直さない。そのため、接続に失敗したまま再試行を続けている古いエージェントが残っていると、再実行しても同じ3分待ちで止まる。手順書の「必要なら `start-agent.bat` を起動」に従うと、同じ名前のエージェントが2つ動く。原因が `-JenkinsUrl`（サーバー自身から名前解決できない名前を指定した場合など）にあるときは、URL を直したコマンドで再実行しなければならず、「同じコマンド」では直らない。古いエージェントが動いている限り、`start-agent.bat` の `-url` も古いまま残る。
- 理由: 読み手は、画面の案内と手順書のどちらに従うか判断できない。手順書に従っても回復しない場合がある。
- 修正案: エージェント行は、スクリプトの表示に合わせる。「エージェントのウィンドウで原因を確認し、そのウィンドウを閉じてから再実行する。Jenkins URL を直した場合は、直した値で再実行する」とする。「再実行の原則」の一文は、Jenkins のウィンドウに限るか、削除する。

### [重要] 無効なプラグインの対処に、Jenkins の再起動が抜けている

- 対象箇所: 「主なエラーと対処（JDK・Jenkins）」の `必要なプラグインが有効ではありません` 行の「Jenkins の Plugins 画面で状態を確認して再実行」
- 問題: スクリプトは、6個のプラグインがすべて入っていれば `OK: all plugins already installed` を返す。この場合は `RESTART required` が付かないため、Jenkins を再起動しない。プラグインを有効にする処理もない。そのため、無効のまま残ったプラグインは、再実行しても有効にならず、同じエラーで止まる。Plugins 画面で有効にしたり、依存関係を直したりした場合も、Jenkins を再起動するまで反映されない。
- 理由: 表の「状態を確認して再実行」だけでは回復しない。原文には「無効のまま残ったものは、Plugins 画面で有効にしてください」とあったが、改稿で弱まった。
- 修正案: 「Plugins 画面で、表示された ID を有効にする（依存関係のエラーがあれば解消する）。Jenkins を再起動してから、同じコマンドで再実行する」とする。

### [重要] 「署名を確認」とあるが、スクリプトは取得物の正しさを確かめていない

- 対象箇所: 「取得物を削除して再実行する場合」の「ダウンロード中にエラーになったファイルや署名を確認できなかったファイルは、スクリプトが削除します。」。「主なエラーと対処（導入）」の「途中の壊れた取得物はスクリプトが削除する」
- 問題: `Test-FileSignature` が見るのは、ファイル先頭の2バイト（EXE は `MZ`、ZIP と WAR は `PK`）だけである。デジタル署名もハッシュも確かめていない。インフラ担当は「署名」を Authenticode などの電子署名と読む。また、ダウンロード中に Ctrl+C を押したりウィンドウを閉じたりすると、`catch` が実行されず、途中までのファイルが残る。先頭2バイトが合っていれば、次回はそのファイルが再利用される。
- 理由: 配布物の真正性を検査済みと誤解させ、通信経路の検査や許可リストを申請するときの判断を誤らせる。壊れた取得物が自動では消えない場合があることも読み取れない。
- 修正案: 「先頭の形式（EXE、ZIP）が合わないファイル」と書く。スクリプトは電子署名やハッシュを確認しないことを明記する。中断した場合は、取得途中のファイルを手で削除する旨を加える。

### [提案] 接続テストが失敗したときの確認に、設定用 PC のプロキシを加える

- 修正案: 手順4に「設定用 PC のプロキシ設定で、Jenkins サーバーが除外されているか」を加える。
- 確認事項: CISetup の実行環境で、`urllib` が Windows のプロキシ設定を使うか、除外リストが効くか。
