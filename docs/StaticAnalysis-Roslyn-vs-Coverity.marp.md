# 1. 静的解析とは？

---

## 静的解析 = 「動かさずにコードを調べる」

- **動的解析**：プログラムを**実行して**バグを探す（テスト・デバッグ）
- **静的解析**：プログラムを**実行せずに**、ソースコードを読んで問題を指摘する

> たとえるなら「文章を読み返して誤字・危険な表現を自動で赤ペンする校正ツール」。

コンパイル（ビルド）と同じタイミングで、コードの「危なそうな書き方」を機械が指摘してくれます。

---

## 何を見つけてくれる？

| 種類 | 例 |
|------|-----|
| バグの芽 | null になりうる変数の参照、後始末（Dispose）忘れ |
| 規約違反 | 命名ルール、書き方の統一 |
| セキュリティ | SQL インジェクションになりうる文字列連結 |
| 品質・可読性 | 使っていない変数、無駄な処理 |

ポイント：**「まだバグになっていないが、いずれ事故る書き方」を早めに教えてくれる。**

---

<!-- _class: lead -->

# 2. なぜ必要なのか

---

## 「後で見つける」ほど高くつく

```
設計 → 実装 → レビュー → テスト → 本番
 安い ────────────────────────► 高い
        ▲
   静的解析はここで自動で拾う
```

- 人のレビューは大事だが、**見落とす／時間がかかる**
- 静的解析は**毎回・自動・同じ基準**でチェックできる
- 早く直すほど修正コストが小さい

> 「レビュアーの負担を減らし、ケアレスミスを機械に任せる」のが静的解析の価値。

---

# 3. 代表的なツール

---

## .NET まわりの静的解析ツール

| ツール | 特徴 |
|--------|------|
| **NetAnalyzers（Roslyn）** | .NET SDK 同梱。CA / IDE ルール。**今の CI で使用** |
| StyleCop.Analyzers | 命名・スタイルを厳しく統一 |
| Roslynator | 可読性・リファクタ向けの大量ルール |
| Security Code Scan | セキュリティ特化 |
| SonarAnalyzer.CSharp | SonarQube 連携のルールセット |

---

## 言語をまたぐ・商用でよく出るもの

| ツール | 特徴 |
|--------|------|
| **SonarQube / SonarCloud** | 品質・セキュリティの定番プラットフォーム |
| **Coverity** | 商用。深い欠陥検出が強い |
| **CodeQL（GitHub）** | クエリベースのセキュリティ解析 |
| Semgrep | ルールベースで軽量・高速 |
| Pylint / Ruff / ESLint 等 | 各言語向け |

<span class="small">大きく分けると「ビルドに載る軽量なアナライザー」と「専用エンジンで深く調べる商用ツール」の2種類。</span>

# 4. Roslyn / NetAnalyzers とは
## （今の設定）

---

## Roslyn アナライザーの位置づけ

- **Roslyn** = .NET のコンパイラ基盤
- その上で動く「コードを検査するプラグイン」が **Roslyn アナライザー**
- **NetAnalyzers** = Microsoft 純正のルール集（`CA****` / `IDE****`）で **SDK に同梱**

> つまり「ビルドすると、ついでに品質チェックもしてくれる」仕組み。追加インストール不要。

---

## 今の CI がやっていること

`dotnet build` に以下を渡し、**全ルールを有効化して検出**しています。

```
-p:EnableNETAnalyzers=true          … アナライザーを起動
-p:AnalysisMode=AllEnabledByDefault … 普段オフのルールも全部 ON
-p:AnalysisLevel=latest             … 最新のルールセット
-p:EnforceCodeStyleInBuild=true     … コードスタイル(IDE)も実行
-p:TreatWarningsAsErrors=false      … 検出はするがビルドは止めない
```

結果は High / Medium / Low に分類して、HTML・Markdown・CSV でレポート化。

---

## NetAnalyzers の得意・不得意

| | 内容 |
|--|------|
| 得意 | 規約、よくある誤用、API の使い方、基本的なバグの芽 |
| 手軽さ | `dotnet build` だけで動く。毎日 CI で回せる |
| 苦手 | 複数ファイル・複雑な経路をまたぐ「深い欠陥」の検出 |

> 「毎日の軽い健康診断」。速くて安く、習慣化できるのが強み。

---

<!-- _class: lead -->

# 5. Coverity とは

---

## Coverity = 深く調べる商用エンジン

- **商用の静的解析（SAST）ツール**
- コードの**実行経路を追いかけて**、深い欠陥を探す
- 得意分野：
  - null 参照、リソースリーク（メモリ・ファイル・接続）
  - 並行処理（デッドロック・競合）
  - 信頼できない入力がどこまで流れるか（セキュリティ）

> 「精密検査・人間ドック」。時間はかかるが、見えにくい重い問題を掘り出す。

---

## Coverity の注意点

| 項目 | 内容 |
|------|------|
| コスト | 商用ライセンスが必要 |
| 速度 | スキャンが重く、別ジョブになりがち |
| 運用 | 指摘の**トリアージ（確認・要否判断）体制**が前提 |

<span class="small">体制なしで入れると、指摘（特に偽陽性）が溜まって「見なくなるツール」になりやすい。</span>

---

# 6. 2つの違い

---

## NetAnalyzers と Coverity の比較

| | NetAnalyzers(Roslyn) | Coverity |
|--|----------------------|----------|
| 種類 | SDK 同梱・無償 | 商用・専用エンジン |
| 強み | 規約・誤用・基本バグ | 深い欠陥・経路解析 |
| 速さ | 速い（毎ビルド） | 重い（別ジョブ） |
| 導入 | `dotnet build` だけ | サーバー／ライセンス |
| たとえ | 毎日の健康診断 | 精密検査・人間ドック |

> **どちらが上ではなく、役割が違う。**

---

<!-- _class: lead -->

# 7. どう選ぶか

---

## 「どっちか」ではなく「重ねる」

```
┌─────────────────────────────────────────┐
│ レビュー / テスト                        │
├─────────────────────────────────────────┤
│ 毎日のゲート：NetAnalyzers(Roslyn)       │ ← 速い・安い・習慣化
├─────────────────────────────────────────┤
│ 深い保険：Coverity など（定期/マージ前） │ ← 重大欠陥を掘る
└─────────────────────────────────────────┘
```

- 日常の品質は **Roslyn** で担保
- 致命傷を減らす追加の保険として **Coverity**
- 「絶対バグ許さない」はツール名でなく、**どの指摘を Fail にするか**で決まる

---

## 判断の軸

| 質問 | Yes なら |
|------|----------|
| .NET 中心で毎日 CI で止めたい？ | まず NetAnalyzers を厳しく運用 |
| 壊れたときの損失が甚大？ | Coverity を足す価値が高い |
| 深い経路バグを人手で拾いきれない？ | Coverity 向き |
| 指摘をトリアージする体制がある？ | Coverity を活かせる |

---

# 8. Coverity を入れるべきタイミング

---

## こういう時は導入価値が高い

1. **影響が大きい領域** — 決済・認証・医療・自動車・組み込み・インフラ制御
2. **要件・コンプライアンス** — 監査や取引先が商用 SAST を要求
3. **深い経路解析が欲しい** — null / リーク / 並行性 / 入力の流れ
4. **既存ゲートで不安が残る** — テスト・レビュー・Roslyn でも深刻な不具合が出る
5. **トリアージ体制がある** — 指摘を確認・優先度付け・管理できる

---

## まだ急がなくてよい時

- 業務 CRUD 中心で、影響範囲が限定的
- まず **NetAnalyzers / テスト / レビュー**の運用が固まっていない
- ライセンスやスキャン時間に見合うほど、深い欠陥の優先度が高くない

> 順番のおすすめ：**Roslyn を厳しく運用 → 足りない部分が明確になってから Coverity。**

---

# 9. 顧客への説明トーク

---

## 3ステップで説明する

1. **現状**
   > 「ビルドのたびに .NET 標準の静的解析（Roslyn/NetAnalyzers）を全ルールで回し、品質を毎日チェックしています。」

2. **限界**
   > 「ただし複数ファイルをまたぐ深い欠陥（リーク・並行性など）は、軽量な解析では拾いきれません。」

3. **提案**
   > 「影響の大きい部分には Coverity のような商用 SAST を重ねると、重大な欠陥を早期に検出できます。」

---

## 想定質問への答え

| 質問 | 答え方 |
|------|--------|
| 今も何かやってる？ | はい、SDK 標準の Roslyn で全ルール検出＋レポート |
| Coverity は必須？ | 影響度・要件次第。まず Roslyn を厳しく運用が基本 |
| 高い？ | 商用ライセンス。得られる安全性と天秤にかける |
| 入れれば安心？ | ツールより**トリアージ運用**が成否を分ける |

# 10. まとめ

---

## この資料の要点

- 静的解析 =「実行せずにコードの危険を指摘する」
- **NetAnalyzers(Roslyn)** = 速い・安い・毎日回す健康診断（今の設定）
- **Coverity** = 重い・深い精密検査（商用）
- 選び方は「どっちか」でなく **重ねる**
- Coverity は **影響が大きい／要件がある／深い欠陥を狙う／体制がある**時に導入
- 「絶対バグ許さない」は、ツール名より **どの指摘を Fail にするか** で決まる

> まずは Roslyn を厳しく運用し、足りない部分に Coverity を重ねるのが堅実。
