# CI 技術報告
## ビルドを「個人作業」から「チームの仕組み」へ

対象: 開発メンバ  
発表者: __________  
日付: __________

---

## 本日のゴール

1. 現在の CI が何を自動化しているか共有する
2. 運用実績から、CI が止めているものを確認する
3. CI を続ける必要性をチームで認識する

> CI は「ビルドを楽にする道具」だけではなく、  
> **品質と再現性をチームで維持するための開発基盤**です。

---

## CI がないと起きやすいこと

| 課題 | 発生する問題 |
|------|--------------|
| 各自の PC で手動ビルド | 環境差・手順差により結果が変わる |
| 確認項目が人に依存 | チェック漏れ、品質のばらつき |
| 失敗の共有が遅い | 問題を含んだ状態で後続作業が進む |
| 成果物を手作業で配布 | 版や作成元が分からなくなる |
| ログが各 PC に散在 | 不具合調査を再現できない |
| 担当者しか手順を知らない | 異動・休暇時に作業が止まる |

これらを「注意する」だけでなく、仕組みで減らすのが CI です。

---

## 1. CI とは

**Continuous Integration（継続的インテグレーション）**

変更を共有場所へ入れるたびに、決めた確認を自動で実行する仕組み。

ソフトウェアだけでなく、FPGA のソースや制約ファイルも対象にできます。

- ソースコードの取得
- ビルド
- Lint・静的解析
- ユニットテスト
- 成果物作成・保管
- ログ保管
- Teams への結果通知

---

## ハード開発に置き換えると

CI は、ソースコードに対する**自動検査ライン**です。

| ハード開発 | CI |
|------------|----|
| 図面・部品表を出図する | ソースを Git に反映する |
| 製造・実装する | ビルド・合成する |
| 検査仕様に沿って確認する | テスト・静的解析を実行する |
| 検査成績書を残す | ログ・レポートを保存する |
| 異常を関係者へ連絡する | Teams に自動通知する |

担当者の経験だけに頼らず、毎回同じ検査を通して記録を残します。

---

## 変更すると、何が起きるか

```text
1. 開発者が変更を Git に反映
2. Jenkins が変更を見つける
3. 専用 PC でビルド・テスト・解析
4. 成果物とログを保存
5. Teams に成功／失敗を通知
```

開発者が毎回コマンドを打つ仕組みではありません。  
一度設定すれば、普段の開発操作をきっかけに自動で動きます。

---

## FPGA でも考え方は同じ

```text
RTL・制約・Tcl を Git に反映
  ↓
Vivado / Quartus で合成・実装
  ↓
エラー、警告、タイミング、使用率を記録
  ↓
bitstream とレポートを保存
  ↓
結果を Teams へ通知
```

「担当者の PC では生成できた」だけでなく、共通環境で再生成できることを確認します。

---

## CI が置き換えないもの

CI は、設計者の判断や実機評価を置き換えるものではありません。

**CI に任せる**
- 毎回同じ手順の反復
- ビルド・合成・テスト・解析
- 成果物、ログ、結果の保存と共有

**人が判断する**
- 仕様と設計の妥当性
- 回路・RTL・ソフトウェアのレビュー
- 実機でしか確認できない性能や安全性

人の判断を減らすのではなく、判断前の確認漏れを減らします。

---

## この資料に出てくるもの

| 名前 | 役割 |
|------|------|
| Git | ソースと変更履歴を共有する保管場所 |
| Jenkins | 変更を見つけ、決めた処理を自動実行する CI サーバー |
| ビルドエージェント | 実際にビルド・合成・テストを行う専用 PC |
| Teams | 結果をチームへ知らせる場所 |
| CISetup | Jenkins の設定をプロジェクトへ導入する社内ツール |

Jenkins が司令役、ビルドエージェントが作業者、CISetup が設定を標準化します。

---

## 現在のシステム構成

```text
開発者
  │ push / merge
  ▼
社内 Git
  │ 変更検知・定期取得
  ▼
Jenkins ──────► Windows ビルドエージェント
                       │
                       ├─ ビルド・テスト・静的解析
                       ├─ 成果物・ログをファイルサーバーへ保存
                       └─ 結果を Teams へ通知

CISetup ──► Jenkins ジョブ・認証情報・CI 設定を反映
```

---

## パイプラインの処理

```text
Checkout
   ↓
Prepare
   ↓
Lint
   ↓
Build
   ↓
Test
   ↓
Static Analysis
   ↓
Publish
   ↓
成果物・解析結果・テスト結果・ログを保存
   ↓
Teams 通知
```

失敗した時点と詳細ログを残し、原因調査につなげます。

---

## 3 つの実行タイミング

| 実行方法 | 目的 |
|----------|------|
| Git の変更検知 | main / master への反映後に早期確認 |
| 定期実行 | 毎日同じ条件で健全性を確認 |
| 手動実行 | リリース前確認、設定変更後の確認 |

同じパイプラインを使うため、実行者による手順差を減らせます。

---

## 自動で残る情報

| 種類 | 主な内容 |
|------|----------|
| 成果物 | exe、zip、FPGA bitstream など |
| ビルドログ | コンパイラ・ビルドツールの全出力 |
| テスト結果 | 成功・失敗件数、失敗テスト名、TRX |
| 静的解析 | High / Medium / Low の指摘と HTML レポート |
| 実行情報 | ビルド番号、対象ブランチ、所要時間、結果 |

> 「いつ・どのコードを・どの手順で処理し・何が起きたか」を追跡可能にします。

---

## 対応範囲

- .NET デスクトップアプリ
  - restore / build / test / static analysis / publish
- FPGA
  - Vivado / Quartus の合成
  - bitstream・レポート・ツールログの回収
- カスタムコマンド
  - C / C++ / Python などへの拡張
- Windows / Linux エージェント
  - 対象プロジェクトとツールチェインに応じて選択

共通部分を再利用し、プロジェクト固有なのは主にビルド手順です。

---

## CISetup を用意した理由

Jenkins を直接設定するだけでは、次の負担が残ります。

- Jenkinsfile や PowerShell の手作業
- ジョブ・Credentials の個別設定
- プロジェクトごとの設定差
- 認証情報を誤って Git に登録するリスク
- 導入担当者への知識集中

CISetup は、これらを GUI と共通テンプレートに集約します。

---

## CISetup が標準化するもの

| 項目 | 標準化内容 |
|------|------------|
| Jenkins ジョブ | 共通テンプレートから作成・更新 |
| ビルド工程 | 共通ステージと共通ログ形式 |
| 通知 | Teams カードの形式を統一 |
| 保存先 | 成果物・ログ・解析・テストを分類 |
| 秘密情報 | Git 追跡対象外の設定へ分離 |
| 導入手順 | GUI、環境チェック、接続テスト |

新しいプロジェクトでも同じ考え方で CI を展開できます。

ここまでが仕組みです。次は、本番の履歴で何が止まったかを見ます。

# 2. 運用で分かったこと
## IPU_TEST_APP の履歴で、CI が止めたものを見る

---

## 運用実績（IPU_TEST_APP）

本番は #17（2026-06-24）から #208（09-28）。導入確認、テストビルド（#25〜#26・#30〜#37・#40・#53〜#55・#106〜#109）、テスト送信は分母に入れない。

| 完了 | 成功 | 失敗 | 成功率 | 異常検出率 |
|------|------|------|--------|------------|
| 173回 | 151 | 22 | **87%** | **13%** |

- 異常検出率は失敗数 ÷ 完了数。CI が処理を止めた割合
- ユニットテストは 116 件（#38、6/30）から 1294 件（#208、9/28）まで増えている
- 導入前の作業時間と、リリース後の発見率は未計測。ここからは検出の記録を見る

---

## 失敗 22 回の内訳

| 要因 | 回数 | 割合 | 主な内容 |
|------|------|------|----------|
| CI環境 | 14 | **64%** | スクリプト、一時失敗、並列、スケジューリング |
| 開発環境・作業 | 8 | **36%** | 手元との差、初期化不足、追加漏れ |

開発環境・作業の 8 回は、手元では進んでいた差と追加漏れ。CI環境の 14 回は、スクリプトと実行時の揺れ。

スケジューリング 8 回のうち、#117・#134・#180 はスレッドで確認済み。#139・#142・#182・#183・#197 は発言が無く、再実行か次のビルドで成功したため同じ扱い。

# 3. なぜ続けるか
## 止めた記録が、チームの確認になる

---

## 8 回は、手元では進んでいた

開発環境・作業の 8 回は、初期化不足、ファイルの有無、追加漏れ、手元だけでの成功。

CI が同じ手順で止め、Teams とログに残した。いずれも次のビルドで成功を確認できている。

担当者が席にいなくても、止まった理由と次の成功をチームで追える。

---

## 13% の読み方

異常検出率 13% は、CI が処理を止めた割合。

そのうち CI環境の 14 回は、スクリプト、一時的な失敗、並列実行、スケジューリング。いずれもその後のビルドで成功している。

後工程ほど修正範囲は広がる、という考え方で読むと、今回の数字はその前段で止めた 22 回。

---

<!-- _class: lead -->

# まとめ

- 取得から通知までを、同じ手順にした
- 173 回のうち 22 回が止まり、8 回は手元との差と追加漏れ
- 残る 14 回はスクリプトと実行時の揺れで、その後のビルドで成功している
- 記録が残るので、次の成功までチームで追える

> CI は追加作業ではなく、  
> **品質を維持しながら開発を続けるための標準工程**です。

---

## おまけ: 直すとしたら

本編の結論ではない。今回の失敗から見える直し方の例。

- スケジューリング 8 回は、時間待ちのテストが CI の負荷で揺れている。待ちをイベント完了に変えると、成功と失敗が分かれにくい
- 手元だけで通るテストは、ファイルの有無や初期化を CI の環境に合わせる。この差は、今回 CI がすでに止めている
